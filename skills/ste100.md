# ASD-STE100 Skill

## Purpose
Explain or rewrite content in **ASD-STE100 Simplified Technical English**. This is a controlled language used in aerospace and defense documentation. It reduces ambiguity and improves translation accuracy.

## Rules (enforced until explicit human statement lifts them)

### Sentence structure
- Maximum **25 words per sentence**. Count every word.
- Use **active voice** by default. One subject performs one action.
- Use **one topic per sentence**. Do not combine unrelated ideas.
- Use **simple verb tenses only**. Avoid perfect and continuous forms.
  - Prefer "The system starts" over "The system has been starting".
  - Prefer "The user clicks" over "The user is clicking".
- Use **one verb per clause**. Avoid compound verbs.

### Vocabulary
- Use **simple, common words**. Avoid jargon when a plain word exists.
  - Prefer "start" over "commence".
  - Prefer "end" over "terminate".
  - Prefer "use" over "utilize".
  - Prefer "check" over "verify" when no formal verification is meant.
- Use **one word per concept**. Do not use synonyms for the same thing.
- Use **exact words from the source domain**. Do not replace technical terms with plain synonyms.
  - "absence", "request", "validation" stay as-is.
  - "DraftKind", "ViewModel", "Bloc" stay as-is.
- Avoid **phrasal verbs** when a single word exists.
  - Prefer "extinguish" over "put out".
  - Prefer "enter" over "go into".
  - Prefer "omit" over "leave out".

### Grammar
- **No -ing forms** used as nouns (gerunds). Use infinitives or rephrase.
  - Prefer "The act of checking" over "Checking".
  - Prefer "To check is to verify" over "Checking verifies".
- **No passive voice** unless the actor is unknown or irrelevant.
  - Prefer "The system rejects the input" over "The input is rejected".
- **No contractions**. Use "do not" not "don't".
- **No abbreviations** on first use. Spell out, then abbreviate in parentheses.
  - First use: "Simplified Technical English (STE)"
  - Later: "STE"
- **No ambiguous pronouns**. Repeat the noun.
  - Prefer "The user clicks the button. The button starts the request." over "The user clicks it. It starts the request."

### Numbers and units
- **Spell out numbers one through nine**. Use digits for 10 and above.
- **Use SI units**. Write the unit symbol after a space.
  - "5 ms" not "5ms".
  - "100 bytes" not "100bytes".
- **Use consistent formatting** for dates, times, and IDs.
  - Dates: "2025-06-24"
  - Times: "14:30"
  - IDs: keep exact format from source

### Formatting
- Use **headings** to separate major topics.
- Use **numbered lists** for sequences or ordered steps.
- Use **bulleted lists** for non-ordered items.
- Use **tables** for comparison data or matrices.
- Use **code blocks** for technical identifiers, class names, and code snippets.
- Use **bold** for UI elements and key terms on first use.
- Use *italics* for emphasis sparingly.

### Technical content
- **Keep all technical terms unchanged**. Class names, method names, variables, and constants stay exactly as written.
- **Preserve all links and references**. Do not alter file paths, package names, or import statements.
- **Preserve all TEST-INTENT markers** exactly. Do not reword `/// see TEST-INTENT "Name"`.
- **Preserve all tables and matrices**. Keep exact column headers and row data.
- **Preserve all code blocks**. Do not modify code content.

## Process

1. **Identify the task**: Explain? Rewrite? Both?
2. **Parse the source**: Extract technical terms, preserve exact names, identify sequences.
3. **Apply rules sentence by sentence**: Check word count, voice, tense, vocabulary.
4. **Review for ambiguity**: Check pronouns, compound ideas, and unclear references.
5. **Verify technical accuracy**: Ensure no meaning was lost or changed.

## Decision Matrix

Return one of:
- **Explain** — Provide a clear explanation in ASD-STE100. Use headings, lists, and examples. Keep technical terms exact.
- **Rewrite** — Rewrite the content in ASD-STE100. Preserve all technical content, tables, code, and references. Apply all style rules.
- **Both** — Provide an explanation first, then the rewritten content.

## Examples

### Bad (not STE100)
"The system's ongoing validation of user inputs has been resulting in the suppression of the submit button, which subsequently prevents the user from accidentally submitting malformed data."

### Good (STE100)
"The system validates user inputs. The validation disables the submit button. This prevents the user from submitting malformed data."

### Bad (not STE100)
"After having clicked the delete button, the user is presented with a confirmation dialog which asks whether they want to proceed with the deletion operation."

### Good (STE100)
"The user clicks the delete button. The system shows a confirmation dialog. The dialog asks whether the user wants to proceed with the deletion."

## Lifting restrictions

Restrictions stay active until the human explicitly says so (e.g., "you can use normal English now", "restrictions lifted", "exit ste100 mode").
